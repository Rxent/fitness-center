## Что вообще такое Django

Django — это набор готовых инструментов на Python для быстрого создания сайтов. Вместо того чтобы руками писать SQL-запросы, обрабатывать формы, проверять пароли — мы описываем **модели** (таблицы БД), **views** (что показать на странице) и **templates** (HTML), а Django делает всё остальное.

Django работает по схеме **MVT** — Model–View–Template:

1. **Model** — класс Python, описывающий таблицу в БД (например, `Client`, `Trainer`).
2. **View** — функция Python, которая запускается при переходе по URL. Она достаёт нужные данные и отдаёт HTML-страницу.
3. **Template** — HTML-файл с подстановками (`{{ variable }}`, `{% if %}`).

Плюс ещё **URL-роутер** — таблица соответствий «адрес → функция-view».

## Структура папок

```
fitness-center/
├── config/           # основные настройки Django-проекта
├── users/            # пользователи и роли (admin/trainer/client)
├── clients/          # профили клиентов (с датой рождения и т.п.)
├── trainers/         # профили тренеров + их специализации
├── subscriptions/    # тарифы, абонементы клиентов, оплаты
├── schedule/         # залы, тренировки, записи на тренировки
├── reports/          # (пока пустое, будет на 3-й неделе — отчёты)
├── templates/        # все HTML-шаблоны страниц
├── manage.py         # точка входа для команд (runserver, migrate и т.п.)
├── requirements.txt  # список библиотек, которые нужны проекту
└── db.sqlite3        # файл БД (создаётся автоматически, в git не хранится)
```

Каждая папка кроме `config/`, `templates/` и `reports/` — это **Django-приложение**. Внутри у каждого приложения одинаковый набор файлов:

| Файл | Зачем нужен |
|---|---|
| `models.py` | Описание таблиц БД (что за поля, какие типы, связи между таблицами). |
| `admin.py` | Настройка того, как эта таблица будет выглядеть в админке `/admin/`. |
| `views.py` | Функции, которые обрабатывают переходы на страницы. |
| `urls.py` | Какой адрес какой функции из `views.py` соответствует. |
| `forms.py` | Описание форм (ввод данных пользователем). |
| `apps.py` | Конфиг приложения (название и что запускать при старте). |
| `migrations/` | Автогенерируемые файлы, которые Django использует, чтобы создать/изменить таблицы в БД. |

## Что где происходит: поток данных

Пример: клиент нажимает «Записаться на тренировку».

1. Браузер шлёт запрос `POST /schedule/5/enroll/`.
2. Django смотрит в `config/urls.py` — там прописано, что всё, начинающееся с `/schedule/`, обрабатывает приложение `schedule`.
3. В `schedule/urls.py` адрес `<id>/enroll/` привязан к функции `enroll()` из `schedule/views.py`.
4. Функция `enroll()`:
   - Проверяет, что пользователь вошёл в систему (декоратор `@login_required`) и у него роль «клиент».
   - Находит `TrainingClass` с нужным id.
   - Проверяет через `_can_enroll()`, что можно записаться (есть абонемент, есть места, тренировка ещё не началась).
   - Если всё ок — создаёт новый `Enrollment` в БД.
   - Делает редирект обратно на страницу тренировки.
5. Браузер получает редирект → заново запрашивает страницу → Django рендерит HTML-шаблон `templates/schedule/class_detail.html` → пользователь видит «Вы записаны».

## Основные модели (что хранится в БД)

### `users.User`
Кастомная модель пользователя (расширяет стандартную Django-шную). Добавлены поля:
- `role` — admin / trainer / client.
- `phone`, `photo`.

Указана в настройках через `AUTH_USER_MODEL = 'users.User'` — это **обязательно** делать до первой миграции, иначе Django создаст таблицу со стандартной моделью и поменять её потом будет тяжело.

### `clients.Client`
Профиль клиента. Связан с `User` через `OneToOneField` — это значит, что каждому клиенту соответствует ровно один пользователь и наоборот. Поля: дата рождения, пол, заметки о здоровье, экстренный контакт, активен ли.

### `trainers.Trainer` и `trainers.Specialization`
Профиль тренера (тоже `OneToOneField` с `User`) + справочник специализаций. Связь «тренер ↔ специализации» — `ManyToManyField` (у одного тренера может быть несколько специализаций и наоборот).

### `subscriptions.SubscriptionPlan`
Справочник тарифов (базовый / стандартный / премиум).

### `subscriptions.Subscription`
Купленный клиентом абонемент. Связи:
- `client` — кому принадлежит (`ForeignKey` на `Client`).
- `plan` — какой тариф (`ForeignKey` на `SubscriptionPlan`).
Поля: `start_date`, `end_date` (считается автоматически), `visits_used`, `status`.

### `subscriptions.Payment`
Факт оплаты. `OneToOneField` на `Subscription` (каждая оплата относится ровно к одному абонементу).

### `schedule.GymRoom`
Зал: название, описание, вместимость.

### `schedule.TrainingClass`
Тренировка: название, тренер (`ForeignKey`), зал (`ForeignKey`), дата-время начала и конца, максимум участников, статус.

### `schedule.Enrollment`
Запись клиента на тренировку. Связывает `Client` и `TrainingClass`. Поле `status` (enrolled/attended/missed/cancelled) позволяет тренеру отмечать посещаемость.

## Роли и права доступа

Роль хранится в поле `User.role`. На каждый URL, где нужна проверка, вешается декоратор из `users/decorators.py`:

- `@admin_required` — только админ или суперюзер.
- `@trainer_required` — только тренер.
- `@client_required` — только клиент.
- `@staff_required` — админ **или** тренер (для общих страниц вроде «Клиенты»).

Внутри декоратор проверяет `request.user.role`. Если роль не подходит — возвращается `403 Forbidden`.

## Автоматическое создание профиля (сигнал)

Когда в админке админ создаёт нового пользователя и выставляет ему `role='trainer'` — отдельно создавать запись в таблице `Trainer` **не нужно**. Это делает **сигнал** `post_save` в `users/signals.py`:

```python
@receiver(post_save, sender=User)
def create_role_profile(sender, instance, created, **kwargs):
    if created and instance.role == 'trainer':
        Trainer.objects.get_or_create(user=instance)
    ...
```

Сигнал — это «крючок»: Django после сохранения `User` автоматически зовёт эту функцию. Регистрация сигнала прописана в `users/apps.py` в методе `ready()`.

## Как работают шаблоны (templates)

Файлы `templates/base.html` + конкретные страницы (например, `templates/schedule/class_list.html`).

- `base.html` — общий каркас: подключён Bootstrap, шапка, футер. В нём блоки `{% block content %}{% endblock %}` — «дырки», куда другие шаблоны подставляют своё содержимое.
- Конкретный шаблон начинается с `{% extends 'base.html' %}` и переопределяет блоки.
- Внутри шаблона:
  - `{{ variable }}` — выводит значение из контекста, переданного из view.
  - `{% if ... %}` / `{% for ... in ... %}` — логика.
  - `{% url 'namespace:name' arg %}` — подстановка URL по имени (чтобы при смене адреса в `urls.py` ссылки в шаблонах не ломались).
  - `{% csrf_token %}` — обязательная штука во всех формах с методом POST (защита от подделки запросов с других сайтов).

## Админка

Django даёт готовую админку по адресу `/admin/`. Чтобы таблица там появилась, надо зарегистрировать модель в `admin.py` своего приложения:

```python
@admin.register(Client)
class ClientAdmin(admin.ModelAdmin):
    list_display = ('user', 'age', 'gender', 'is_active')
    list_filter = ('gender', 'is_active')
    search_fields = ('user__first_name', 'user__last_name')
```

- `list_display` — какие колонки показывать в списке.
- `list_filter` — фильтры сбоку.
- `search_fields` — поля, по которым искать (двойное подчёркивание `user__first_name` значит «поле `first_name` у связанной модели `user`»).

## Команда `seed_demo`

Написана в `users/management/commands/seed_demo.py`. Это **management command** — свой аналог `migrate` и `runserver`. Запускается так:

```
python manage.py seed_demo
python manage.py seed_demo --reset    # удалить всё и создать заново
```

Внутри команда через `get_or_create()` добавляет в БД: специализации, тарифы, залы, демо-пользователей, демо-абонементы, демо-тренировки, демо-записи. `get_or_create` возвращает либо уже существующий объект, либо создаёт новый — поэтому команду можно запускать сколько угодно раз, дубликатов не будет.

## Миграции

Когда я меняю модель (добавил поле, изменил тип) — надо:

```
python manage.py makemigrations   # Django создаёт файл с описанием изменений
python manage.py migrate          # Django применяет эти изменения к БД
```

Файлы миграций лежат в `<app>/migrations/` и **должны быть в git** (чтобы у тебя и у меня структура БД совпадала).

## Запуск проекта с нуля

```bash
python -m venv .venv                       # создать виртуальное окружение
source .venv/bin/activate                  # активировать (Windows: .venv\Scripts\activate)
pip install -r requirements.txt            # поставить зависимости
python manage.py migrate                   # создать таблицы в БД
python manage.py seed_demo                 # заполнить демо-данными
python manage.py runserver                 # запустить dev-сервер на http://127.0.0.1:8000/
```

Демо-логины (пароль у всех `demo12345`):
- `demo_admin` — администратор, он же суперюзер.
- `demo_trainer1`, `demo_trainer2`, `demo_trainer3` — тренеры.
- `demo_client1` … `demo_client4` — клиенты.

## Куда смотреть, если что-то сломалось

- **500-я ошибка в браузере** → страница с ошибкой (в DEBUG=True) прямо покажет файл и строку. Читать по-английски снизу вверх.
- **Шаблон не отрендерился** → проверить, что путь в `render(request, 'app/file.html', ...)` совпадает с реальным путём в `templates/`.
- **`TemplateDoesNotExist`** → забыл создать файл или опечатка в пути.
- **`NoReverseMatch`** → в `{% url '...' %}` указал несуществующее имя маршрута или не передал нужный аргумент.
- **`FieldError: Cannot resolve keyword`** → в запросе к модели указал поле, которого нет (опечатка или забыл `makemigrations`).
- **Форма не сохраняется** → забыл `{% csrf_token %}` или `request.method == 'POST'` в view.
